# 순수 Java로 작은 Spring 만들기

2026-11-06에 `simple-tomcat` 내장 서버 기반의 [Spring 생태계 조사와 구현 로드맵](../README.md)을 정리했다. 현재는 조사 단계이며 구현 코드는 없다. 실제 Spring 소스 기준·서버 선행 조건·단계별 완료 기준은 새 문서를 참고한다. 아래는 기존 주문 예제 중심의 실습안이다.

이 프로젝트의 첫 실습은 주문 서비스에 저장소를 연결하는 것이다. 처음에는 두 객체를 직접 만든다. 이후 같은 주문 코드와 테스트를 유지하면서 객체를 만드는 일, 연결하는 일, HTTP 요청에서 호출하는 일을 차례로 프레임워크에 옮긴다. 각 단계가 끝날 때 **“방금까지 내가 하던 일 중 무엇을 이제 프레임워크가 하는가?”**에 코드 한 곳을 짚어 답해 보자.

학습 환경은 Java 17 이상, Gradle, JUnit Jupiter를 기준으로 제안한다. 예제는 `example.order`, 재사용할 프레임워크 코드는 `minispring` 패키지에 둔다. 의존 방향은 예제에서 프레임워크 쪽으로만 향하게 한다. 핵심 과정은 JDK와 테스트 라이브러리만으로 진행할 수 있다.

## 1. 주문 하나를 손으로 조립한다

`OrderRepository`에 `save`와 `findById`를 정의하고, `Map`을 사용하는 `InMemoryOrderRepository`를 만든다. `OrderService`는 생성자로 저장소를 받아 주문을 저장하고 주문 번호를 반환한다. 첫 테스트의 형태는 다음과 같다.

```java
var repository = new InMemoryOrderRepository();
var service = new OrderService(repository);

var id = service.placeOrder("연필", 2);

assertEquals(2, repository.findById(id).orElseThrow().quantity());
```

테스트에서 저장소를 기록용 가짜 객체로 교체해 보자. 서비스 코드를 고치지 않고도 저장 요청을 관찰할 수 있다면 이미 생성자 의존성 주입(DI)을 사용한 것이다. 이제 실행용 조립 코드를 `main`에 두고, 새 서비스가 같은 저장소를 써야 할 때 누가 그 인스턴스를 전달하는지 확인한다.

## 2. 객체 등록과 생성을 분리한다

`MiniBeanFactory`에 `register(type, supplier)`와 `getBean(type)`을 만든다. 먼저 저장소의 생성 방법을 등록하고, 서비스의 생성 함수에서는 팩터리에 저장소를 요청한다. 등록된 생성 방법과 이미 생성한 인스턴스는 서로 다른 맵에 둔다. 첫 조회 때 생성하고, 이후 조회에는 같은 인스턴스를 반환한다.

**통과 기준** — 같은 팩터리에서 두 번 조회하면 `assertSame`이 통과하고, 새 팩터리에서 만든 저장소는 별개다. 미등록 타입을 요청하면 메시지에 그 타입이 나온다. 이 단계에서 빈은 컨테이너가 관리하는 객체이며, 싱글턴의 범위는 이 컨테이너 하나다. [Spring IoC 컨테이너와 빈](https://docs.spring.io/spring-framework/reference/core/beans/introduction.html)

## 3. 생성자에서 의존 관계를 읽는다

2단계에서는 서비스마다 생성 함수를 써야 했다. 이제 `register(OrderService.class)`처럼 구현 클래스를 등록하고, 리플렉션으로 생성자의 매개변수 타입을 읽는다. 각 타입에 대입 가능한 등록 후보 하나를 찾아 재귀적으로 생성한 뒤 생성자를 호출한다. 첫 버전은 클래스마다 공개 생성자 하나만 허용한다. 서비스는 컨테이너의 존재를 몰라도 된다.

**통과 기준** — 서비스와 저장소 구현 클래스만 등록해도 1단계 주문이 저장된다. 저장소 후보가 0개이거나 2개이면 어떤 생성자 인자를 결정하지 못했는지 보고한다. 생성 중인 타입을 경로에 기록해서 순환 의존이 생기면 `A → B → A`를 출력한다.

## 4. 애너테이션으로 등록 대상을 고른다

런타임에 읽을 수 있는 타입 애너테이션 `@MiniComponent`를 만든다. 먼저 후보 클래스 목록을 직접 전달해 표시된 클래스만 3단계의 등록 함수로 보낸다. 이 테스트가 통과하면 지정한 패키지의 컴파일 출력 디렉터리에서 후보를 찾는 스캐너를 붙인다. 첫 범위는 디렉터리로 한정하고 JAR 탐색은 확장 과제로 둔다.

**통과 기준** — 저장소와 서비스에 표시를 붙이면 개별 등록문 없이 주문 테스트가 통과한다. 저장소의 표시를 지우면 3단계에서 만든 후보 누락 오류가 재현된다. 여기까지 완성하면 독립적으로 사용할 수 있는 작은 IoC 컨테이너가 생긴다.

## 5. HTTP 요청을 컨테이너의 객체에 전달한다

먼저 네트워크 없이 `dispatch("GET", "/orders/count")`를 테스트한다. 컨트롤러는 주입받은 서비스를 통해 주문 수를 반환한다. 처음에는 메서드와 경로를 직접 등록하고, 다음으로 `@MiniGet`에 적힌 경로를 읽어 같은 라우팅 표를 만든다. 별도 simple-tomcat 프로젝트의 서블릿 컨테이너에 디스패처를 연결한다. 서버는 요청을 읽고 응답을 쓰며, 디스패처는 호출할 메서드를 고른다.

**통과 기준** — 서비스로 주문 한 건을 저장한 뒤 실제 HTTP 요청을 보내면 상태 200과 본문 `1`을 받는다. 모르는 경로는 404, 같은 경로와 HTTP 메서드의 중복 등록은 시작 시 오류로 처리한다. 실제 Spring MVC에서는 서블릿 컨테이너가 요청을 받고 `DispatcherServlet`이 공통 처리 흐름을 조율한다. [Spring MVC의 DispatcherServlet](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet.html)

## 마무리 실습

빈 종이에 두 흐름을 따로 그린다. 첫 번째는 시작할 때 어떤 클래스가 발견되고 연결되는지, 두 번째는 주문 수 조회 요청이 어떤 객체를 거쳐 응답이 되는지다. 각 화살표 옆에 자신이 만든 메서드 이름을 적는다. 마지막으로 실제 Spring 예제에 같은 주문 서비스를 연결하고, 직접 작성한 코드 중 어떤 부분을 생성자 주입과 요청 매핑이 대신했는지 대조한다.
