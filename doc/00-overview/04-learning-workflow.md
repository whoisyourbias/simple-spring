# 학습 단계의 필수 규약

기준일: 2026-11-06. 이 프로젝트에서 단계의 정당성은 “Spring에 있는 기능인가”보다 **“직전 산출물의 어떤 문제를 해결하는가”**로 먼저 판단한다. 사용자에게 명시적으로 받은 최우선 목표다.

## 1. 단계의 구성

| 항목 | 반드시 답할 내용 |
|---|---|
| 이전 산출물 | 어느 직전 버전의 어떤 파일·객체·요청에서 시작하는가 |
| 한계 재현 | 어떤 입력·새 요구·변경으로 불편·오류·누수·수정 확산을 관찰하는가 |
| 손으로 해볼 해결 | 기존 코드에 가장 작게 고쳐 볼 수 있는 방법은 무엇인가 |
| 최소 변경 | 반복되는 어떤 책임만 프레임워크로 옮기는가 |
| Spring 대응 | 고정 버전의 클래스·메서드·실제 호출 순서와 어떤 관계인가 |
| 전후 검증 | 같은 업무 fixture에서 무엇을 유지하고 어떤 관찰이 개선되는가 |
| 경계·실패 | 새 책임의 상태·예외·정리 계약을 무엇으로 확인하는가 |
| 남겨둘 다음 문제 | 지금 산출물에 구체적으로 무엇이 남아 다음 단계의 시작이 되는가 |
| 범위·선행 조건 | 아직 제공하지 않는 기능과 서버·소스 조사 조건은 무엇인가 |

첫 단계는 출발 기준선이므로 이전 구현이 없다. 주 과정 마지막은 다음 단계를 강제로 만들지 않고 완주 또는 명시한 확장 문제로 연결한다.

## 2. 문제는 실제로 겪어야 한다

“DI를 구현한다”, “Spring에도 HandlerAdapter가 있다”는 단계의 출발 이유가 아니다. 두 endpoint가 서로 다른 repository를 보고, constructor 하나를 바꾸는데 recipe도 고치고, handler 형태가 늘 때 Dispatcher에 타입 분기를 추가해야 하는 식으로 이전 코드에서 재현한다.

원래 잘 동작하던 버전에 새 요구를 붙였을 때 드러난 제약을 그 버전의 버그라고 쓰지 않는다. 수동 설정이 맞게 동작하는 단계에서 일부러 잘못된 상태를 정상 완료로 남기지도 않는다. 새 요구를 추가한 별도 실험으로 한계를 드러낸다.

한 단계가 끝날 때 학생은 “내가 하던 어떤 일이 어느 메서드로 옮겨졌고, 그 메서드를 누가 언제 부르는가”를 답해야 한다. 그 답이 클래스 이름 나열뿐이면 단계를 다시 설계한다.

## 3. 전후 검증의 세 층

1. **한계 실험:** 직전 버전에서 실행한다. 생성·init·close·advice 횟수, 서로 다른 객체 참조, 수정해야 하는 위치, 실제 HTTP 상태 등 관찰값을 기록한다.
2. **개선 실험:** 같은 fixture와 요구에서 지금 버전이 책임을 넘겨받은 것을 확인한다. 예: 집계 객체 생성 1→0, main의 개별 close 목록 제거, 새 handler 추가 시 Dispatcher 수정 0곳.
3. **회귀 실험:** 기존 주문 결과·정상/실패 전파·객체 정체성·자원 정리가 유지되는지 확인한다. 외부 응답이 같은 리팩터링도 변경 범위·소유권 개선을 입증하면 의미가 있다.

수정 위치 수는 설계 차이를 이해하기 위한 기록이지 특정 파일 개수에 맞춘 테스트를 무조건 작성하라는 뜻은 아니다. 구현 세부를 그대로 복사한 테스트를 늘리지 않고 공개 계약과 책임 경계를 검증한다.

## 4. 구현 전에 저장할 것

단계별 설계·계획에는 위 항목에 더해 변경 파일·지원 입력·구체적인 테스트·실행 명령을 적는다. 기준 버전은 Framework v6.2.1·Boot v3.4.1·Tomcat 10.1.34를 따른다. 해당 기능의 실패 분기까지 추가 확인하고 미확인에 의존하지 않는다.

진행 상태는 계획/구현/검증을 구분한다. 미래 클래스·태그·실행 명령을 현재 사용할 수 있다고 쓰지 않는다. 완료 시 실제 검증 결과·차이·다음 문제를 단계 설명과 현재 현황에 반영한다.

## 5. 하나의 과정과 확장 과정

주 과정은 같은 HTTP 주문 앱에서 수작업을 누적해서 없앤다. AOP 뒤에 전혀 새로운 웹 입문을 시작하지 않는다. scope·full configuration·트랜잭션·HTML View·WebFlux는 주 과정의 어느 상태에서 어떤 요구가 생겼는지를 [확장 과정](05-extension-tracks.md)에 명시한다.

의존 관계만 있다고 인과관계가 생기지는 않는다. “AOP 다음은 트랜잭션” 대신 “주문만 저장되고 재고는 실패했다 → 한 연결에서 수동 rollback → 모든 저장소의 연결 공유 → 서비스 경계 interceptor”로 이어져야 한다.

## 6. 단계 번호와 기록

현재 순서는 [00~19 로드맵](03-implementation-roadmap.md), 선택 확장은 E01~E05다. 문서가 생기는 시점에만 학습 폴더를 만들고 빈 폴더는 만들지 않는다.

코드 구현 시 각 단계의 코드·검증·학습 문서를 함께 보존하는 체크포인트를 만든다. 이전 버전 한계 실험이 기본 테스트를 상시 실패시키지 않게 정상 회귀와 분리한다. 실제 브랜치·태그 명칭과 보존 방법은 첫 구현 계획에서 확정한다. 현재 해당 코드나 태그는 없다.
