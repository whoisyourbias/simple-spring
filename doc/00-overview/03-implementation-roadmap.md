# 문제를 해결하며 만드는 Spring — 새 학습 순서

재설계일: 2026-11-06. 사용자의 “각 다음 단계가 이전 단계의 문제를 해결한다”를 기준으로 기존 순서를 폐기하고 다시 구성했다. **아래는 앞으로 구현할 학습 과정이며 구현 완료 기록이 아니다.**

기준: Spring Framework v6.2.1·Boot v3.4.1·Tomcat 10.1.34. S번호의 실제 클래스·메서드·고정 소스는 [대응표](../reference/03-learning-stage-mapping.md)에 있다. [학습 규약](04-learning-workflow.md), [확장 과정](05-extension-tracks.md), [서버 계약](../reference/01-embedded-tomcat-contract.md), [차이·미확인](../reference/02-implementation-status.md)을 함께 읽는다.

## 과정의 출발점

처음부터 같은 HTTP 주문 앱을 사용한다. 최초에는 한 Servlet과 직접 new한 서비스·저장소만 있다. 앱을 늘리면서 생긴 조립·수명·호출·표현·시작의 수작업을 한 번에 하나씩 프레임워크로 옮긴다. 코어를 모두 만든 후 새 웹 프로젝트를 시작하지 않는다.

각 단계의 “다음 문제”는 다음 단계의 입력이다. 새 요구를 추가해서 드러난 한계는 기존 기능의 버그와 구분한다. 반드시 응답이 틀려야만 문제가 되는 것은 아니다. 같은 결과를 위해 여러 곳을 고쳐야 하거나 init/close를 사람이 기억해야 하는 것도 재현 가능한 문제다.

P0: Java 21·Maven Wrapper·JUnit과 **실제 동작하는 simple-tomcat의 자체 Servlet·프로그램 등록·내장 start/getPort/close·수명 계약**을 확인한다. 현재 서버는 HTTP/Adapter까지이므로 이 전제는 아직 미충족이다. P0 전에는 순수 Java 준비 실험만 할 수 있고 실제 HTTP 단계 완료로 표시하지 않는다. 없는 API의 시그니처를 계획에서 확정하지 않는다.

공통 fixture는 주문 0개/1개/여러 개와 동일 repository 정체성이다. 주문 변경은 fixture 또는 서비스로 하고 기본 HTTP는 읽기 요청이다. 각 단계에서 이전 정상 요청과 자원 정리 회귀를 유지한다.

## 한눈에 보는 문제의 연결

| 00 | 수동 HTTP 기준선이 없다 | Servlet·직접 객체 조립 |
| 01 | 두 화면이 다른 주문을 본다 | 공통 조립과 생성자 주입 |
| 02 | 진입점별 조립 복사·고정 반환 묶음이 커진다 | 완성 객체 등록과 선택적 조회 |
| 03 | 안 쓰는 집계 객체도 미리 만든다 | 생성 정의와 singleton 캐시 |
| 04 | recipe에 constructor 의존 관계를 다시 적는다 | 자동 생성자 DI |
| 05 | 클래스마다 등록 목록을 고친다 | component 탐색과 정의 등록 |

| 11 | URL 추가 때 공통 Servlet을 고친다 | Dispatcher·HandlerMapping |

| 19 | 기본 구성 반복과 사용자 정의 충돌 | 조건부 자동 구성·back-off |

## 단계별 재현과 해결

### 00 — 우선 프레임워크 없이 주문 수를 HTTP로 보여 준다

- **이전 산출물:** P0에서 검증한 내장 서버와 빈 프로젝트.
- **한계 재현:** 아직 프레임워크의 필요를 경험할 앱이 없다. /orders/count 한 경로를 끝까지 실행할 기준선을 만든다.
- **손으로 해볼 해결:** OrderHttpServlet 안에서 repository와 service를 직접 new하고 경로를 if로 분기한다. fixture에서 주문을 준비한다.
- **최소 변경:** 새 추상화 없음. 앱의 Servlet·업무 코드·실행 main과 HTTP 회귀 테스트만 만든다.
- **Spring 대응:** S37. 이 단계는 Spring 구현이 아니라 이후 비교할 수동 기준선이다.
- **전후 검증:** 주문 0개에서 본문 0, 같은 service로 한 건 추가한 뒤 같은 GET에서 1. 실제 임시 포트의 200·UTF-8·정상 종료를 확인한다.
- **경계·실패:** 미등록 경로 404, 업무 예외 뒤 다음 요청 복구. main과 Servlet 안의 new 위치를 기록한다.
- **남겨둘 다음 문제:** 요약 화면도 추가하려고 같은 방식으로 endpoint를 하나 더 조립하면, 각자 만든 repository가 서로 다른 주문을 보게 된다.
- **범위·선행 조건:** HTTP 실행은 P0 통과 후에만 한다. 주문 변경은 서비스 호출·fixture로 수행하며 GET으로 쓰기 작업을 하지 않는다.

### 01 — 두 화면이 서로 다른 주문을 보는 문제를 고친다

- **이전 산출물:** 00의 단일 경로 앱에 /orders/summary를 추가하려는 상태.
- **한계 재현:** count용·summary용 객체를 각각 new하고 count 쪽 service로 주문을 추가한다. count는 1인데 summary의 주문 수는 0인 것을 재현한다.
- **손으로 해볼 해결:** 두 endpoint의 constructor에 같은 repository를 전달한다. 생성 코드를 main 한 곳으로 모은다.
- **최소 변경:** 명시적인 composition root만 만든다. OrderService 등 업무 객체는 생성자 인자를 받을 뿐 컨테이너를 모른다.
- **Spring 대응:** S03~S05가 나중에 대신할 조립 책임과 비교한다. 수동 생성자 DI도 DI라는 점을 확인한다.
- **전후 검증:** 전에는 1/0이던 두 경로가 1/1이 되고 repository 참조도 동일하다. 원래 count 테스트를 유지한다.
- **경계·실패:** 다른 앱 인스턴스는 별도 repository를 사용한다. 업무 객체의 전역 static 저장소로 공유 문제를 덮지 않는다.
- **남겨둘 다음 문제:** 같은 주문 객체 그래프를 HTTP main과 집계 실행 main에서 각각 조립하면 new 코드가 복사된다. 공통 조립 함수로 줄여도 각 실행부가 필요한 entry를 받기 위한 고정 반환 묶음이 계속 커진다.
- **범위·선행 조건:** 프레임워크나 singleton API를 아직 도입하지 않는다.

### 02 — 실행 진입점마다 복사한 객체 조립을 한곳에 등록한다

- **이전 산출물:** 01의 수동 조립 코드와 이를 복사한 집계 진입점.
- **한계 재현:** 먼저 collaborator 변경 때 두 main의 new 코드 수정 위치를 센다. 공통 조립 함수로 이를 해결한 뒤 새 집계 entry를 추가한다. 실행부마다 필요한 객체가 다른데 고정 반환 묶음·조립 결과 타입·소비 코드를 함께 늘려야 하는 선택적 조회의 한계를 확인한다.
- **손으로 해볼 해결:** 공통 함수로 조립 중복을 먼저 없앤다. 반환 객체 묶음을 계속 확장하는 대신 완성 객체를 이름으로 등록해 각 실행 경계가 필요한 entry만 꺼내게 한다.
- **최소 변경:** 완성 객체의 registerSingleton/getBean에 해당하는 최소 registry를 추출한다. 업무 객체는 생성자 DI를 유지하고 registry는 조립 경계에서만 사용한다.
- **Spring 대응:** S06의 registerSingleton/addSingleton. 외부에서 이미 만든 객체를 등록하는 경로다.
- **전후 검증:** 객체 조립 변경은 공통 등록 위치 한 곳이다. 새 집계 entry를 등록·조회할 때 기존 HTTP main과 고정 반환 묶음의 수정이 필요 없어진다. 같은 이름 재조회와 두 HTTP 화면의 동일 repository를 검증한다.
- **경계·실패:** 없는 이름·다른 타입·중복 이름 등록을 명확히 실패시킨다. 컨테이너별 객체 표는 격리한다.
- **남겨둘 다음 문제:** 객체 표를 채우려면 사용하지 않는 집계 객체까지 먼저 new해야 한다. count만 조회해도 무거운 집계 객체의 생성 횟수가 1이다.
- **범위·선행 조건:** 수동 등록 객체의 init/destroy를 자동 수행한다고 약속하지 않는다. Spring의 정의 기반 bean 생성과 구분한다.

### 03 — 아직 쓰지 않는 객체를 시작할 때 전부 만드는 일을 없앤다

- **이전 산출물:** 02의 완성 객체 표. 선택 집계 객체도 등록 시점에 이미 만들어진다.
- **한계 재현:** 집계 객체 constructor에 생성 카운터를 두고 count만 조회한다. 집계 객체가 한 번도 사용되지 않았는데 생성된 것을 관찰한다.
- **손으로 해볼 해결:** 객체 대신 생성 함수를 표에 넣고 조회할 때 호출한다. 그대로 두면 같은 이름 조회마다 새 객체가 생기는 문제도 비교한다.
- **최소 변경:** 빈 정의와 완성 singleton 캐시를 분리한다. 이름별 생성 recipe와 생성 상태를 관리하는 작은 BeanFactory로 발전시킨다.
- **Spring 대응:** S02·S06. 같은 정의의 singleton은 한 번 완성해 캐시하고 실패 결과는 노출하지 않는다.
- **전후 검증:** count만 조회할 때 집계 생성 1→0, 집계를 처음 조회한 뒤 1, 다시 조회해도 1. 같은 클래스의 다른 이름 정의와 다른 factory는 별개다.
- **경계·실패:** 생성 함수 실패 뒤 캐시·생성 중 표시가 남지 않는다. 동시 singleton 조회를 지원할 때 생성 횟수 1을 검증한다.
- **남겨둘 다음 문제:** 지연 생성은 됐지만 모든 recipe에 getBean 호출로 의존 관계를 손으로 다시 적고 있다. constructor 변경 때 recipe도 고쳐야 한다.
- **범위·선행 조건:** 아직 singleton만 지원한다. prototype은 E01의 상태 섞임 문제에서 도입한다. BeanFactory의 지연 조회와 나중 Context의 선행 초기화를 혼동하지 않는다.

### 04 — 생성 함수에 다시 적은 의존 관계를 생성자에서 읽는다

- **이전 산출물:** 03의 생성 recipe마다 service와 repository 연결을 손으로 작성한 상태.
- **한계 재현:** OrderService의 constructor에 collaborator를 추가한다. 업무 constructor와 별도로 recipe의 getBean 목록을 고쳐야 하는 중복을 재현한다.
- **손으로 해볼 해결:** 리플렉션으로 단일 constructor의 인자 타입을 읽어 유일한 대입 가능 후보를 찾고 재귀적으로 조회한다.
- **최소 변경:** 클래스 정의 등록과 생성자 의존성 해결을 추가한다. 이름·정의·캐시는 03의 것을 유지한다.
- **Spring 대응:** S03~S06. 의존 빈부터 생성하고, 생성자 순환과 해결할 수 없는 후보는 원인을 보존해 실패한다.
- **전후 검증:** 지원하는 클래스의 constructor 의존성을 추가해도 별도 생성 recipe를 수정하지 않는다. 이전 singleton 정체성·두 HTTP 결과를 유지한다.
- **경계·실패:** 후보 0개, 구별 조건 없는 동등 후보 2개, constructor 예외, A→B→A 순환을 검증한다. 생성 중 상태를 finally에서 정리한다.
- **남겨둘 다음 문제:** new와 연결 코드는 줄었지만 클래스를 하나 추가할 때마다 등록 목록을 또 고쳐야 한다. 표시한 새 endpoint도 목록에서 빠지면 발견되지 않는다.
- **범위·선행 조건:** 공개 constructor 하나·유일 후보라는 지원 입력을 명시한다. primary/qualifier/이름/여러 constructor 전체 규칙은 추가 조사 전 지원하지 않는다.

### 05 — 클래스 추가 때마다 등록 목록을 고치는 일을 줄인다

- **이전 산출물:** 04의 클래스 등록 목록과 constructor DI.
- **한계 재현:** @MiniComponent로 표시한 OrderRecentEndpoint를 추가하고 목록 등록을 생략한다. 클래스가 있어도 getBean은 찾지 못하는 것을 재현한다.
- **손으로 해볼 해결:** 명시 후보 목록에서 표시된 타입을 고른 뒤, 같은 탐색을 지정한 패키지의 컴파일 디렉터리에 적용한다.
- **최소 변경:** component 후보를 BeanDefinition으로 등록하는 스캐너를 추가한다. 탐색과 인스턴스 생성은 분리한다.
- **Spring 대응:** S07·S39. 리소스/metadata에서 후보를 찾고 이름·scope 등 정의 정보를 등록한다.
- **전후 검증:** 표시한 새 클래스는 개별 등록문 추가 없이 조회되고 표시하지 않은 타입은 등록되지 않는다. scan만 수행한 시점의 업무 생성 횟수는 0이다.
- **경계·실패:** 중복 이름과 잘못된 후보를 시작 시 보고한다. 후보 탐색 중 static 초기화를 일으키지 않는다. 지원 디렉터리 밖 JAR은 미지원으로 명시한다.
- **남겨둘 다음 문제:** 감사 로그용 외부 FileAuditSink fixture는 수정할 수 없고 생성 인자도 필요하다. 애너테이션 스캔만으로는 이 객체를 등록할 수 없다.
- **범위·선행 조건:** 컴파일된 타입을 초기화 없이 읽는 구체적 방법·이름 충돌 정책은 단계 구현 계획에서 소스를 더 확인한다. JAR 전체 탐색은 별도 확장이다.

### 06 — 수정할 수 없는 외부 객체도 생성 정의로 등록한다

- **이전 산출물:** 05의 component 탐색과, 직접 표시할 수 없는 감사 sink.
- **한계 재현:** 외부 패키지의 FileAuditSink fixture를 service가 요구하도록 하고 자동 탐색만 실행한다. 후보 누락을 확인한다.
- **손으로 해볼 해결:** 조립 경계에 명시 factory method를 만들고 파일 경로 등 인자를 그곳에서 제공한다.
- **최소 변경:** 설정 클래스의 factory method를 BeanDefinition으로 읽는다. method 인자는 기존 DI로 해결하고 반환 타입·factory 위치를 정의에 보관한다.
- **Spring 대응:** S05·S08·S40. 첫 설정 방식은 proxyBeanMethods=false에 대응하는 lite configuration이다.
- **전후 검증:** 외부 타입을 수정하지 않고 등록·주입한다. 설정 method 두 번의 빈 조회는 같은 singleton이고, 내부 업무 클래스 등록 목록은 늘어나지 않는다.
- **경계·실패:** factory method 예외와 인자 누락을 원인과 함께 보고한다. 직접 설정 method 호출을 singleton 조회처럼 취급하지 않는다.
- **남겨둘 다음 문제:** 객체를 만들 수는 있지만 sink의 open/close를 main이 따로 호출해야 한다. 새 자원이 생길 때마다 준비·해제 목록이 늘어난다.
- **범위·선행 조건:** FileAuditSink는 수명 실험용 외부 타입 fixture이며 실제 라이브러리를 이미 선정한 것이 아니다. full configuration은 E02에서 직접 method 호출 문제로 다룬다.

### 07 — 객체마다 main에 적던 준비와 해제를 생성 경계로 옮긴다

- **이전 산출물:** 06의 외부 자원 빈과 main의 수동 open/close 목록.
- **한계 재현:** sink를 조회한 뒤 준비 호출을 빼면 사용이 실패하고, 종료 목록에서 빠뜨리면 열린 자원이 남는 것을 카운터로 재현한다.
- **손으로 해볼 해결:** getBean의 생성 경계에서 지원 init callback을 부르고, 성공적으로 관리된 자원의 destroy callback을 기록한다.
- **최소 변경:** 정의 기반 빈의 초기화·파괴 책임을 BeanFactory로 옮긴다. 생성 의존 관계도 추적해 dependent를 dependency보다 먼저 정리한다.
- **Spring 대응:** S02·S03·S06. 아직 BPP가 없는 지원 부분집합에서 constructor/주입→init→완성 객체 노출을 검증한다.
- **전후 검증:** main의 개별 자원 준비·해제 목록이 사라지고 init 1회·destroy 1회가 기록된다. 재조회·반복 close로 횟수가 늘지 않는다.
- **경계·실패:** init 실패 빈을 완성 singleton으로 캐시하지 않는다. init 내부에서 확보하다 실패한 자원의 정리는 해당 객체의 책임도 명시한다. 수동 registerSingleton 객체와 구분한다.
- **남겨둘 다음 문제:** 자원 수명은 관리하지만 빈은 여전히 첫 조회 때 준비된다. 서버를 먼저 켜면 설정 오류가 첫 실제 요청의 500으로 늦게 드러난다.
- **범위·선행 조건:** InitializingBean/DisposableBean에 대응하는 명시 callback부터 다룬다. annotation callback과 모든 destroy 추론은 추가 조사 없이 약속하지 않는다.

### 08 — 첫 사용자 요청에서 발견되던 설정 오류를 시작 중에 발견한다

- **이전 산출물:** 07의 지연 factory와, 먼저 서버를 시작한 뒤 endpoint를 조회하는 main.
- **한계 재현:** 필수 빈의 init을 실패시킨다. 기존 흐름은 listener가 열린 뒤 첫 요청에서야 실패하며 그 전에 만든 자원을 놓칠 수 있다.
- **손으로 해볼 해결:** 서버 시작 전에 필수 빈을 조회하고 실패 시 생성한 자원을 정리하는 try/finally를 작성한다.
- **최소 변경:** 정의 준비와 non-lazy singleton 선행 생성·시작 실패 정리를 refresh로 묶는 ApplicationContext를 만든다. 기존의 선택 집계 빈은 정의에 lazy=true를 명시하고 필수 HTTP 경로의 빈은 non-lazy로 둔다. Servlet/서버 시작은 아직 main이 명시적으로 조정한다.
- **Spring 대응:** S04·S08·S10. 정의 처리 후 일반 빈을 생성하고 refresh 실패 시 관리된 singleton을 파괴·실패 전파한다.
- **전후 검증:** 필수 빈 init 실패가 첫 요청→refresh로 이동한다. 실패 시 업무 요청 수락 0회와 이미 초기화한 자원 destroy를 검증한다. 정상 refresh 뒤에는 기존 HTTP 응답과 명시 lazy 집계 빈의 미사용 생성 횟수 0을 유지한다.
- **경계·실패:** 생성 도중 실패, 반복 close, 의존 순서 정리를 검증한다. non-lazy 소비자가 lazy 빈을 constructor로 요구하면 그 의존 빈은 생성된다. 정의의 lazy는 자동 지연 proxy가 아니며 prototype 여부와도 다르다.
- **남겨둘 다음 문제:** 시작은 정리됐지만 서비스 메서드마다 실행 시간·실패 기록을 복사한다. 공통 기록 정책 하나를 바꾸려면 여러 업무 메서드를 고쳐야 한다.
- **범위·선행 조건:** 이 시점에는 BPP 목록이 비어 있다. 10에서 후처리기를 추가할 때 refresh의 일반 빈 생성 전에 준비해야 한다. Boot의 내부 서버 기동 순서를 구현했다고 주장하지 않는다.

### 09 — 업무 메서드마다 복사한 기록 코드를 프록시로 감싼다

- **이전 산출물:** 08의 Context와 서비스 메서드에 흩어진 실행 기록.
- **한계 재현:** 조회·집계 메서드마다 붙인 시간 기록을 바꾸고, 정상·예외 경로의 중복 위치와 누락을 비교한다.
- **손으로 해볼 해결:** 수동 decorator로 감싼 뒤 서비스 인터페이스의 메서드가 늘 때 반복되는 위임을 JDK 동적 프록시로 줄인다.
- **최소 변경:** 수동 interceptor chain·proxy를 만들고 기존 대상 서비스마다 명시 factory 정의에서 proxy를 반환하도록 연결한다. 모든 기존 소비자가 그 proxy를 받게 한 뒤 업무 객체의 공통 기록을 제거한다. 포장할 대상과 연결은 사람이 등록한다.
- **Spring 대응:** S12. 명시 factory method에서 수동으로 제공한 proxy와 조건에 따른 컨테이너 자동 proxy를 구분한다. 이 시점에는 자동 proxy 후처리기가 없다.
- **전후 검증:** 직접 호출과 모든 기존 HTTP 경로에서 before→target→after가 한 번씩 기록되고 반환·예외·기록 계약을 유지한다. 업무 메서드의 기록 중복만 제거하며 수동 포장 정의는 남는다.
- **경계·실패:** 대상 예외의 타입·cause를 보존하고 finally 기록을 확인한다. 자기 호출은 proxy를 우회한다. JDK proxy는 인터페이스 기준으로 사용한다.
- **남겨둘 다음 문제:** 같은 기록 정책이 필요한 새 OrderExportService를 component로 추가하면 객체는 자동 생성되지만 사람이 포장 정의를 추가하지 않는 한 기록이 빠진다. 기존 경로는 정상인데 새 서비스마다 수동 포장 설정을 기억해야 한다.
- **범위·선행 조건:** 예제의 service target은 별도 수명 callback이 없는 객체이며 자원 의존 빈은 07의 관리를 유지한다. component 원본과 수동 proxy를 같은 의존 타입 후보로 중복 등록하지 않는다. 모든 서비스 타입의 자동 AOP라는 주장은 10 전까지 하지 않는다.

### 10 — 새 서비스의 프록시 포장 누락을 생성 후처리로 해결한다

- **이전 산출물:** 09의 모든 기존 소비자가 수동 proxy를 쓰는 앱과 새 서비스를 추가하려는 상태.
- **한계 재현:** 새 OrderExportService를 기존 component 방식으로 추가하고 같은 기록 요구를 적용한다. 기존 경로는 기록되지만 새 경로는 포장 등록을 빠뜨리면 기록 횟수가 0이다. 별도 신규 요구 실험이며 09의 기존 기록 회귀는 계속 통과해야 한다.
- **손으로 해볼 해결:** 새 서비스에도 명시 포장 factory를 추가해 정상화한다. 대상마다 같은 설정을 반복하는 대신 조건 판정·포장을 빈 생성의 마지막 반환 지점 한 곳으로 옮긴다.
- **최소 변경:** BeanPostProcessor와 자동 proxy 후처리를 추가한다. 초기화 뒤 반환된 최종 객체를 singleton으로 노출하고 constructor DI도 그 참조를 받게 한다.
- **Spring 대응:** S03·S10~S12·S41. refresh에서 BPP를 일반 빈보다 먼저 등록하며 init 전·후 순서를 보존한다.
- **전후 검증:** 새 서비스는 개별 포장 설정 없이 기록된다. 같은 빈을 직접 getBean한 참조와 서로 다른 endpoint에 주입한 참조는 같은 최종 proxy다. 09의 수동 포장 정의를 제거해도 모든 기존 기록과 HTTP 결과를 유지한다.
- **경계·실패:** 수동 포장이 남아 이중 proxy/advice가 생기지 않는지 확인한다. 후처리기 등록 전 이미 생성한 객체를 사후 재포장했다고 주장하지 않는다. init 예외·proxy 생성 실패·반환값·자기 호출을 검증한다.
- **남겨둘 다음 문제:** 객체 생성과 공통 서비스 처리는 자동화됐지만 OrderHttpServlet의 URL if/else는 그대로다. /orders/recent를 추가하려면 공통 Servlet을 수정해야 한다.
- **범위·선행 조건:** 일반적인 순환 없는 인터페이스 기반 proxy부터 지원한다. early proxy·클래스 proxy와 BPP 자동 탐색의 모든 정렬 규칙은 별도 조사한다.

### 11 — URL을 추가할 때마다 공통 Servlet을 고치는 일을 없앤다

- **이전 산출물:** 10의 관리 endpoint들과 OrderHttpServlet의 경로 분기.
- **한계 재현:** 새 업무 경로를 추가하면서 같은 Servlet의 if/else·404·공통 진입 코드를 함께 수정하는 범위를 기록한다.
- **손으로 해볼 해결:** URL→handler 표를 Servlet 바깥에 등록하고 공통 Servlet은 표에서 handler를 찾아 호출하게 한다.
- **최소 변경:** DispatcherServlet과 명시 HandlerMapping을 추출한다. 처음에는 동일한 요청/응답 처리 계약의 handler만 지원한다.
- **Spring 대응:** S13. Tomcat은 기본 매핑 /의 Servlet을 고르고, MVC 계층은 업무 handler를 고른다.
- **전후 검증:** 새 handler와 mapping 등록만 추가해 /orders/recent가 동작한다. Dispatcher 구현 변경 0곳, 기존 경로 응답과 빈 참조는 유지된다.
- **경계·실패:** 미등록 경로 404, handler 예외 뒤 정상 요청 복구. 요청 상태가 다음 요청으로 새지 않도록 한다.
- **남겨둘 다음 문제:** 기존 handler 인터페이스를 구현하지 않는 외부 summary 객체의 method도 연결해야 한다. 지금 Dispatcher의 강제 형변환으로는 호출할 수 없다.
- **범위·선행 조건:** Servlet은 Tomcat이 init/destroy하고 업무 빈은 Context가 소유한다. Dispatcher가 endpoint를 직접 new하지 않는다.

### 12 — handler 모양이 늘 때마다 Dispatcher에 타입 분기를 넣지 않는다

- **이전 산출물:** 11의 단일 handler 형태와 명시 mapping.
- **한계 재현:** 같은 요청/응답을 받되 인터페이스를 구현하지 않는 legacy method handler를 등록한다. 기존 캐스팅의 한계를 확인한다.
- **손으로 해볼 해결:** 등록마다 wrapper를 작성하거나 Dispatcher에 instanceof를 추가해 본다. handler 종류 하나 추가 때 반복되는 위치를 기록한다.
- **최소 변경:** supports/handle 계약의 HandlerAdapter를 추출한다. 기존 인터페이스 handler와 명시적으로 지정한 method handler의 호출을 각각 담당한다.
- **Spring 대응:** S13·S16. handler 선택과 호출 방법 선택을 분리한다. 초기 method handler는 native 요청/응답을 받는 void method로 범위를 좁힌다.
- **전후 검증:** 두 handler 형태가 같은 Dispatcher를 거쳐 동작한다. 세 번째 형태는 새 adapter와 등록으로 추가하고 Dispatcher 본문은 수정하지 않는다.
- **경계·실패:** handler 없음 404와 adapter 없음의 설정 오류를 구분한다. reflection 래퍼 대신 대상 예외를 전달한다.
- **남겨둘 다음 문제:** Dispatcher 수정은 사라졌지만 method가 있는 곳과 URL·HTTP 메서드 등록표 두 곳에 같은 연결 정보를 적고 있다. 이름 변경 때 등록표가 어긋난다.
- **범위·선행 조건:** 아직 임의 인자·일반 반환값을 지원하지 않는다. argument resolver와 return value handler를 필요 전에 모두 만들어 넣지 않는다.

### 13 — 메서드와 별도 URL 등록표가 어긋나는 문제를 줄인다

- **이전 산출물:** 12의 method handler와 main의 명시 URL 등록표.
- **한계 재현:** endpoint method를 바꾸고 등록표 수정을 빼먹는다. 시작 시 잘못된 연결 또는 누락을 재현한다.
- **손으로 해볼 해결:** method 가까이에 HTTP 메서드·정확 경로를 표시하고 시작 시 이를 읽어 기존 mapping 표로 변환한다.
- **최소 변경:** 자체 Controller/RequestMapping metadata와 HandlerMethod 등록을 추가한다. 실행 대상은 bean 이름으로 관리 객체를 조회한다.
- **Spring 대응:** S14~S16·S20·S38. class/method 조건 결합·등록 충돌·404/405 구별을 보존한다.
- **전후 검증:** 새 endpoint method와 표시만 추가하면 개별 URL 등록문 없이 요청이 연결된다. 같은 Service와 proxy 참조가 유지된다.
- **경계·실패:** 동일 조건의 서로 다른 handler는 시작 실패. 경로 없음 404, method 불일치 405·Allow, GET의 HEAD·OPTIONS 의미를 검증한다. 표준 오류는 작은 고정 처리 경로로 먼저 지원한다.
- **남겨둘 다음 문제:** method 연결은 자동화됐지만 limit 같은 query 인자를 읽고 숫자로 바꾸는 코드가 각 method에 반복된다. 누락·잘못된 값 처리도 서로 다르다.
- **범위·선행 조건:** 정확 경로와 명시 메서드 조건부터 지원한다. path template·wildcard·구체성 비교는 미확인 규칙을 확인한 후 별도 확장한다.

### 14 — 요청 인자를 읽고 변환하는 코드를 업무 메서드에서 빼낸다

- **이전 산출물:** 13의 method handler와 각 method의 query 읽기·숫자 변환.
- **한계 재현:** /orders/recent?limit=2와 새 집계 query에서 반복하는 파싱·필수값 검사·400 처리를 비교한다. 누락·문자 입력으로 서로 다른 동작을 재현한다.
- **손으로 해볼 해결:** 공통 파싱 함수로 모은 뒤, method 매개변수 선언을 보고 필요한 인자를 공급하는 방법으로 바꾼다.
- **최소 변경:** ArgumentResolver와 필요한 타입 변환 경계를 추가한다. 우선 명시 이름의 필수 문자열·정수와 native 요청/응답만 지원한다.
- **Spring 대응:** S16·S38·S42. 인자 해결→지원 범위의 변환→target 호출 순서이며 해결 불가능한 인자는 임의 null로 넘기지 않는다.
- **전후 검증:** 업무 method에서 request 조회·정수 파싱 코드가 사라진다. limit=2는 동일 결과, 누락·잘못된 정수는 일관된 400이며 handler 호출은 0회다.
- **경계·실패:** 지원하지 않는 인자 선언은 설정 오류로 드러낸다. 원문 query·반복 값·빈 값의 선택은 소스 확인 후 테스트로 고정한다.
- **남겨둘 다음 문제:** 입력은 업무 값으로 받지만 결과는 여전히 response에 직접 써야 한다. 문자열·JSON 응답을 늘릴수록 header·직렬화 코드가 업무 method에 반복된다.
- **범위·선행 조건:** 진입 조건 Q: 서버의 query parameter 디코딩·문자셋·반복 값 계약을 먼저 구현·검증한다. 현재 서버는 미지원이므로 이 조건 전에는 14를 완료할 수 없다. JSON 요청 body는 포함하지 않는다.

### 15 — 응답 header와 직렬화를 업무 반환값에서 분리한다

- **이전 산출물:** 14의 인자 주입과 업무 method 안의 response 쓰기.
- **한계 재현:** 주문 수 문자열과 집계 DTO JSON 응답에 반복된 Content-Type·본문 쓰기 코드를 수정해 보고 업무 로직과 표현이 섞인 범위를 기록한다.
- **손으로 해볼 해결:** 공통 응답 쓰기 함수를 만든 뒤, 반환형·명시 ResponseBody 선언으로 결과 처리기를 선택한다.
- **최소 변경:** ReturnValueHandler와 HttpMessageConverter 경계를 추가한다. native response를 직접 처리하는 handler도 유지한다.
- **Spring 대응:** S16·S18·S19. ResponseBody의 문자열 본문과 일반 Controller의 문자열 view 이름은 의미가 다르다.
- **전후 검증:** 본문 handler는 값만 반환하고 header/직렬화 중복은 사라진다. 문자열·JSON DTO의 상태·Content-Type·UTF-8 본문이 전후 동일하고 지원하지 않는 응답 표현은 406이다.
- **경계·실패:** 모든 Object를 toString으로 쓰지 않는다. 일반 Controller의 문자열을 조용히 본문으로 보내지 않고 View 미지원 선언으로 드러낸다. 변환기·직렬화 실패의 원인을 보존한다.
- **남겨둘 다음 문제:** 출력 형식은 일관됐지만 업무 예외를 HTTP 상태·오류 본문으로 바꾸는 try/catch가 여러 handler에 남아 있다.
- **범위·선행 조건:** JSON 응답만 다룬다. 직렬화 라이브러리는 이 단계 계획에서 버전을 고정한다. View는 E04, RequestBody는 서버 body 확장 이후 별도 작업이다. 미디어 협상 세부는 구현 전 추가 조사한다.

### 16 — 각 handler가 반복하던 업무 예외의 HTTP 변환을 모은다

- **이전 산출물:** 15의 값 기반 결과 처리와 handler별 업무 예외 catch.
- **한계 재현:** 같은 OrderNotFound 예외를 여러 경로가 서로 다른 상태·본문으로 바꾸는 것을 재현한다. 공통 오류 정책 변경 위치를 센다.
- **손으로 해볼 해결:** 공통 catch 함수로 모은 뒤 예외 유형별 처리기를 등록한다. 13~14의 고정 표준 오류 처리도 같은 경계로 옮긴다.
- **최소 변경:** 순서가 있는 HandlerExceptionResolver 경계를 추가한다. 처리 완료와 다음 resolver 위임, 미해결 예외의 바깥 전파를 구분한다.
- **Spring 대응:** S13의 processHandlerException·S38. 처리된 오류와 미처리 오류를 성공 반환과 섞지 않는다.
- **전후 검증:** 업무 method의 반복 catch가 사라지고 같은 예외가 같은 HTTP 응답이 된다. 미해결 예외는 서버 500 경계까지 전파되고 다음 요청은 정상이다.
- **경계·실패:** 첫 해결자에서 멈춤, resolver 자체 실패, 이미 작성한 미커밋 본문 정리, reflection cause 보존을 검증한다. 전송 완료 뒤 재응답은 약속하지 않는다.
- **남겨둘 다음 문제:** 예외 처리는 모였지만 선택된 handler의 정보에 따라 실행 전 검사를 하고 완료 기록을 남기는 코드가 여러 method에 반복된다.
- **범위·선행 조건:** 서버의 응답 buffer/reset 계약을 확인한다. 현재 memory response에서 검증한 범위를 표준 Servlet commit·ERROR dispatch 전체와 동일하다고 기록하지 않는다.

### 17 — 선택된 handler의 전후 처리와 예외 시 정리를 체인으로 만든다

- **이전 산출물:** 16의 공통 결과·예외 처리와 handler별 전후 검사·완료 기록.
- **한계 재현:** handler metadata에 따른 데모 승인 검사와 요청 완료 기록을 여러 method에 붙인다. 중단·업무 예외 때 완료 기록이 누락되거나 중복되는 것을 재현한다.
- **손으로 해볼 해결:** 선택된 handler 호출을 함수로 감싼 뒤 여러 전후 처리를 순서대로 연결한다.
- **최소 변경:** HandlerExecutionChain·HandlerInterceptor를 추가하고 Mapping→Adapter→pre→handler→post→결과/예외→completion의 동기 흐름으로 정리한다.
- **Spring 대응:** S13·S17. pre 정순, post/completion 역순이며 completion은 pre가 true로 끝난 interceptor만 대상이다.
- **전후 검증:** method 안의 전후 처리 중복이 사라진다. A pre→B pre→handler→B post→A post→B completion→A completion을 검증한다.
- **경계·실패:** B가 false이면 handler/post 0회·A completion만 실행. handler 예외 시 post 생략, 해결/미해결 예외의 completion 인자, callback 실패 뒤 정리 지속·다음 요청 복구를 검증한다.
- **남겨둘 다음 문제:** 요청 처리는 확장 지점으로 옮겨졌지만 main은 Context·후처리·MVC 전략·Servlet·서버·종료를 직접 순서대로 조립한다. 두 앱 main에 같은 시작 코드가 복사된다.
- **범위·선행 조건:** 데모 검사는 Spring Security 구현이 아니다. 서버 Filter와 handler 선택 뒤 interceptor의 위치를 구분한다. async dispatch는 E05의 별도 조건이다.

### 18 — 앱마다 복사한 시작과 종료 순서를 실행 계층으로 옮긴다

- **이전 산출물:** 17의 완성된 동기 요청 파이프라인과 main의 수동 시작·정리.
- **한계 재현:** 작은 두 번째 실행 앱에 같은 구성·refresh·Servlet 등록·서버 시작·shutdown 코드를 복사한다. init 실패와 포트 충돌에서 두 main의 정리 차이를 재현한다.
- **손으로 해볼 해결:** 공통 launch 함수로 모은 뒤 Context와 서버의 준비·요청 수락·실패 정리 단계를 나눈다.
- **최소 변경:** MiniApplication.run·WebServerFactory·웹 Context lifecycle을 만든다. 이 단계의 구성은 여전히 명시적이며 자동 구성은 아직 없다.
- **Spring 대응:** S01·S10·S21~S25. onRefresh에서 서버 준비, 나머지 singleton 초기화 뒤 lifecycle에서 요청 수락. 초기화 중 일부 빈의 이른 조회를 허용하되 후처리 순서를 지킨다.
- **전후 검증:** 앱 main은 앱 설정과 실행 진입만 지정한다. 두 앱의 동일한 시작 순서·실제 포트·HTTP 결과·정상 종료를 확인하고 수동 정리 복사를 제거한다.
- **경계·실패:** factory 0개/복수, 필수 빈 init 실패, 포트 충돌의 원인 전파와 빈·Servlet·worker·포트 정리. 활성 요청이 사용하는 빈을 먼저 파괴하지 않는 순서를 검증한다.
- **남겨둘 다음 문제:** 시작 코드는 공통화됐지만 두 앱이 기본 server factory·mapping·adapter·converter 같은 동일한 구성 선언을 반복한다. 기본값을 제공하면 사용자 정의와 충돌한다.
- **범위·선행 조건:** 진입 조건 B: Tomcat의 준비·bind·수락 분리 계약을 먼저 계획·검증한다. 현재 Endpoint 생성자의 즉시 bind를 Boot와 동일하다고 처리하지 않는다. 전체 외부 설정·nested JAR loader는 별도 범위다.

### 19 — 기본 구성을 제공하면서 사용자 설정이 이기게 만든다

- **이전 산출물:** 18의 공통 실행 계층과 앱마다 반복한 명시 기본 구성.
- **한계 재현:** 두 앱의 공통 server/MVC 정의를 기본 묶음으로 옮긴 뒤 사용자 factory도 등록한다. 단순 무조건 등록은 중복·덮어쓰기 또는 잘못된 factory 선택을 만든다.
- **손으로 해볼 해결:** 사용자 정의가 있는지 먼저 확인하는 조건을 붙이고, 객체 생성 대신 정의·타입 정보로 판단한다.
- **최소 변경:** imports 후보·사용자 정의 선등록·조건 평가·기본 정의 등록의 자동 구성 경계를 만든다. 처음에는 class/bean 조건과 핵심 server/MVC 묶음에 집중한다.
- **Spring 대응:** S08·S26·S27. 기본값의 back-off와 정의 처리 시점이 핵심이다. 조건 검사를 위해 업무 빈을 먼저 만들지 않는다.
- **전후 검증:** 기본 앱은 반복 구성 선언 없이 실행되고 사용자 factory 앱은 사용자 객체를 쓴다. 사용자 빈이 아직 생성되지 않아도 기본 factory는 등록되지 않는다.
- **경계·실패:** 클래스 부재, 사용자 정의 존재, 자동 구성 간 순서·제외를 검증한다. 원인 보고에서 왜 기본값이 빠졌는지 확인한다. 등록 완료 후 일반 빈 생성이 진행된다.
- **남겨둘 다음 문제:** 주 과정은 여기서 완주한다. 새 요구는 E01~E05의 출발 문제로 선택한다. 모든 프로젝트를 한 직선의 다음 단계로 이어 붙이지 않는다.
- **범위·선행 조건:** 전체 Boot 구성 목록·정렬 알고리즘·PropertySource 우선순위·binder는 추가 조사 대상이다. 이번 과정은 직접 정한 지원 조건부터 실제 소스에 맞춘다.

## 주 과정의 완료 판정

19까지 같은 주문 앱이 유지되고, 생성·의존성·수명·공통 호출·URL 연결·인자·본문 응답·오류·전후 처리·시작·기본 구성의 책임이 어디로 옮겨졌는지 실제 파일과 호출 추적으로 설명할 수 있어야 한다.

각 단계는 이전 버전의 한계 실험, 현재 버전의 개선 실험, 기존 동작 회귀를 갖는다. 해당 단계 코드·테스트·문서를 함께 보존하는 체크포인트를 구현 때 만든다. 아직 태그·코드·실행 결과는 없다.

현재 구현되어 있는지, 아직 서버 조건이 막혀 있는지는 [진행 상황](01-progress.md)을 따른다. 구현 전에 단계별 파일·API·소스 분기·실제 명령을 구체화한 계획을 저장한다. 이 문서에 적힌 예정 실험을 테스트 통과 기록으로 사용하지 않는다.
