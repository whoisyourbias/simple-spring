# 문제를 해결하며 발견하는 Spring 학습 과정 설계

작성일: 2026-11-06. 사용자의 단계 전면 재창조 지시에 따른 문서 설계다. Java 구현을 시작하는 설계는 각 단계 착수 전에 별도로 구체화한다.

## 의도와 성공 조건

가장 중요한 목표는 **매 다음 단계가 이전 단계의 구체적인 한계를 해결하며 Spring의 필요성과 동작을 발견하는 것**이다. 클래스 목록·기능 목록을 순서대로 구현하는 과정은 이 목표를 충족하지 못한다.

한 단계는 이전 버전에서 재현할 수 있는 문제를 가지고 시작한다. 손으로 고치는 최소 시도를 거쳐 그 해결이 반복될 때만 프레임워크 책임으로 추출한다. 완료 시 같은 업무 요청이 계속 동작하고, 해당 수작업·누수·중복·변경 범위가 어떻게 줄었는지 확인한다. 다음 문제는 현재 산출물에 실제로 남아 있는 것으로 적는다.

## 고려한 방식과 이번 선택

| 방식 | 장점 | 목표와의 관계 |
|---|---|---|
| 기존 기능별 순서에 문제 설명만 추가 | 수정량이 적음 | AOP 다음 웹 도입·한 단계에 여러 문제 등 기존 단절이 남아 배제 |
| 콘솔 IoC를 끝낸 뒤 웹 과정을 새로 시작 | 서버 준비 없이 바로 코어 구현 가능 | 두 개의 독립 입문 흐름이 되어 기존 문제의 연속성이 약함 |
| 처음부터 작은 HTTP 주문 앱을 유지하고 수작업을 하나씩 옮김 | 객체·요청·기동 문제가 같은 코드에서 누적됨 | 이번 설계의 선택. 웹 서버 준비가 선행되어야 하는 비용을 명시 |

사용자는 문제 해결 중심 재설계를 지시했다. 위 구체적인 앱 구성·단계 분할은 그 요구를 실현하기 위한 설계자의 선택이다.

## 공통 앱과 변하지 않는 계약

- 업무 코드는 `example.order`, 프레임워크는 `minispring`에 둔다.
- 출발점은 `/orders/count` 하나를 처리하는 자체 Servlet이다. OrderService와 InMemoryOrderRepository를 직접 조립한다.
- 이후 `/orders/summary`, `/orders/recent`를 같은 앱에 추가한다. 주문 준비·변경은 fixture나 서비스 호출로 수행하고 GET은 읽기만 한다.
- 기본 과정은 요청 body가 필요 없다. query 인자는 해당 단계 전에 서버의 parameter parsing 계약을 준비한다.
- 객체 공유가 필요한 두 endpoint는 같은 컨테이너의 같은 repository를 사용한다. HTTP 응답·프록시 적용·생명주기 사건을 함께 관찰한다.
- 프레임워크에 책임을 옮겨도 업무 의미·기존 요청 결과·기존 실패 계약을 보존한다. 새 요구에 대한 기존 버전의 한계를 기존 기능의 버그로 바꾸어 설명하지 않는다.

## 과정 구성

P0는 빌드·테스트·자체 Servlet·내장 서버 공개 API가 실제로 준비됐는지 확인하는 선행 점검이다. 현재 simple-tomcat은 이 조건을 아직 만족하지 않는다. 학습 00은 프레임워크 없는 HTTP 앱, 01~10은 같은 앱의 객체 조립·생성·수명·프록시, 11~17은 요청별 수작업, 18~19는 시작과 기본 구성의 수작업을 해결한다.

20개 장면은 구현 작업의 개수를 의미하지 않는다. 하나의 장면 안에서도 실패 실험→최소 해결→추출→검증 작업을 나눌 수 있다. 세부 버그나 메서드 하나를 추가할 때마다 학습 단계 번호를 늘리지는 않는다.

확장은 주 과정의 특정 산출물에서 출발한다. E01은 반복 작업의 상태 섞임에서 scope, E02는 설정 메서드 직접 호출에서 full configuration, E03은 주문·재고의 부분 반영에서 transaction, E04는 HTML 요구에서 View, E05는 느린 소비자·연결 수명에서 reactive로 이어진다. 하나의 직선에 모든 생태계를 억지로 묶지 않는다.

## 실제 Spring에 맞출 핵심

Framework v6.2.1·Boot v3.4.1·Tomcat 10.1.34 기준을 유지한다. 출처는 [소스 대응표](../../../doc/reference/03-learning-stage-mapping.md)에 둔다.

- 수동 singleton 등록과 정의 기반 생성·callback 관리를 구분한다.
- 정의의 이름별 singleton 정체성, 생성 실패 캐시 방지, 생성자 의존성 실패를 보존한다.
- resource init/destroy와 refresh의 시작 실패 정리를 구분해 학습한다.
- BPP 도입 시 init 전·후 순서와 최종 proxy 주입을 보존한다. 이미 생성한 객체를 나중에 무조건 재포장하지 않는다.
- Servlet 수명은 Tomcat, 업무 빈 수명은 Context가 소유한다.
- handler 선택·호출·인자·반환값·예외·interceptor는 필요가 드러날 때 분리하되 최종 동기 dispatch 순서를 보존한다.
- Boot식 실행은 refresh 중 서버 준비·lifecycle에서 요청 수락·시작 실패 정리를 포함한다.
- 자동 구성은 사용자 정의를 먼저 반영하고 조건이 맞을 때 기본 정의를 추가한다.

## 한계와 구현 진입 조건

현재 없는 자체 Servlet API를 가상의 확정 메서드로 명시하지 않는다. P0에서 실제 API·버전·기동·종료 계약을 고정한 뒤 00을 구현한다. 그 전에 순수 Java 준비 실험은 가능하지만 00 완료라고 기록하지 않는다.

현재 서버는 본문·query decoding·async·streaming·지연 bind를 제공하지 않는다. 각 기능에 의존하는 단계 앞에 서버 점검 조건을 둔다. 표준 API 비호환과 초기 서버 수명 차이를 학습용 단순화로 지우지 않는다.

Spring의 전체 API·모든 annotation·JAR 스캔·CGLIB·전체 설정·Reactive Streams 구현은 별도 조사 대상이다. 지원 입력을 좁히되 그 입력의 핵심 동작은 실제 구현과 맞춘다. 차이·영향·후속은 구현 현황에 기록한다.

## 산출물과 검증

현재 읽을 단계는 로드맵 한 곳에 둔다. 공통 학습 규약·확장 과정·소스 대응은 별도 문서에서 담당한다. 초기안은 history로 옮기고 현재 안내와 단계 번호를 모두 동기화한다.

검토 기준은 00~19의 모든 전환에서 이전 산출물과 새 문제의 연결을 설명할 수 있는지, 전후 관찰과 회귀 검증이 있는지, 핵심 동작과 서버 선행 조건을 지키는지다. 문서 링크·소스 ID·번호를 기계적으로 검사한다. 실제 Java 검증 결과와 문서 검증 결과를 섞지 않는다.
